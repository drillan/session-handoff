# handoff-load — 過去の引き継ぎを読み込む

過去のセッションが `handoff` で書いた引き継ぎを読み、作業を再開できる状態にする。
**このスキルはファイルを書き換えない。**

## 自発的に呼ばない

人間が明示的に呼んだときだけ動く。

新規セッションで何を始めるかは、こちらからは分からない。無関係な作業に古い引き継ぎを
持ち込むと、存在しない前提を抱えたまま作業が進む。害のほうが大きい。

## 手順

### 1. 引き継ぎのあるディレクトリを決める

`${CLAUDE_PLUGIN_DATA}/<project-slug>/`。`<project-slug>` は次で得る。

```bash
printf 'cwd=%s\nslug=%s\n' "$(pwd)" "$(pwd | sed 's#[^a-zA-Z0-9_-]#-#g')"
```

置換規則は `pre-compact.sh` と `handoff` に一致させてある。組み立て直さない。

止まるべき条件が 2 つある。いずれも、そこで止めて何が起きているかを報告し、
**手順 2 へ進まない**。どちらも「引き継ぎが無い」と報告してはならない場面で、
無いと言い切ると人間は誤った前提のまま作業を始める。

- **`${CLAUDE_PLUGIN_DATA}` が絶対パスに展開されておらず `${CLAUDE_PLUGIN_DATA}` という
  文字列のまま見えている。** このシェル変数は Bash ツールの環境には存在しないので、
  シェル経由でも解決できない。推測して探すと、「引き継ぎが無い」のか「見に行った場所が
  違う」のか区別がつかなくなる
- **`cwd` が、セッション開始時にシステムから提示された作業ディレクトリと違う。**
  Bash ツールの作業ディレクトリはセッション中の `cd` で移動し、そのまま保持される。
  移動後に呼ぶと別 slug のディレクトリを見に行き、実際には引き継ぎがあるのに
  `NO_DIR` になる。上と同じ誤報を、別の経路で起こす

### 2. 候補を集める

```bash
d=<手順1で確定したディレクトリ>
[ -d "$d" ] || { echo "NO_DIR"; exit 0; }
[ -n "$(ls "$d"/*.md 2>/dev/null)" ] || { echo "NO_FILES"; exit 0; }
[ -f "$d/latest" ] && printf 'latest=%s\n' "$(cat "$d/latest")"
for f in "$d"/*.md; do
  printf '%s\t%s\t%s\t%s\n' \
    "$(basename "$f" .md)" \
    "$(sed -n 's/^updated: //p' "$f" | sed 's/[ \t]*#.*$//; s/[ \t]*$//' | head -1)" \
    "$(sed -n 's/^continues_from: //p' "$f" | sed 's/[ \t]*#.*$//; s/[ \t]*$//' | head -1)" \
    "$(sed -n '/^## いま何をしているか$/,/^## /{ /^## /d; /^$/d; p; }' "$f" | head -1)"
done
```

出力は `session_id`／`updated`／`continues_from`（無ければ空）／
`## いま何をしているか` の先頭 1 行、のタブ区切り。

`## いま何をしているか` は §5.1 で固定された見出し文字列で、`session-start.sh` と
`handoff` も同じ文字列に依存している。**言い換えると抽出が静かに失敗する**ので、
上のコマンド中のこの文字列を書き換えないこと。

値から行末コメントを落としているのは、`lib.sh` の `frontmatter_value`（フックが使う）が
そうしているのに合わせるため。落とさないと、コメント付きの `continues_from` が
どの session_id にも一致しない値になり、**エラーも出ないまま連鎖が切れて**
候補一覧に同じ作業が二重に並ぶ。`continues_from` が存在する理由そのものの失敗が、
無警告で起きることになる。`updated` 側も同じ理由で落とす（この値から経過時間を計算する）。

### 3. 引き継ぎが無ければそこで終わる

`NO_DIR` または `NO_FILES` なら「このプロジェクトの引き継ぎは無い」と報告して終了する。

**他の場所を探し始めない。** 別プロジェクトのディレクトリ、`~/.claude/projects/` の
memory、git のログ、それらしい名前の markdown — どれも引き継ぎではない。
無いものを埋めようとすると、人間は「読み込めた」と受け取ったまま、
実際には無関係な材料の上で作業を始めることになる。

### 4. 候補一覧を出して人間に選ばせる

`continues_from` で連なるファイル群は、**生きているものごとに 1 件へ畳む**。
畳んだ件数を併記する（件数はその行が代表する連鎖の全ファイル数。
複数の行が同じ祖先を共有する場合は、それぞれの行で数える）。

連鎖は「同じ作業を新規セッションで仕切り直した」履歴なので、続きとして意味を持つのは
生きている末端だけ。畳まないと、`## いま何をしているか` がほぼ同じ項目が並び、
どれが最新の続きか判別できなくなる。

**「生きている」の判定は 2 つ。どちらかに当たれば候補として出す。**

- **葉**、つまり他のどのファイルからも `continues_from` で参照されていないもの
- **自分の子孫のいずれかより `updated` が新しい非葉**。開いたままのセッションが、
  後継が作られたあとも自分のファイルを更新し続けている状態で、作業としてはまだ動いている

比較相手は「自分の子孫」であって「連鎖の葉のうち最新のもの」ではない。
枝分かれしていると葉が複数あり、どの葉と比べるかで結論が変わってしまう。

`updated` が最大のものを選ぶのでもない。葉が基準で、それより新しい非葉を足す。

**生きているものが複数あるときは 1 件に畳まない。それぞれを 1 件として出す。**
同じ引き継ぎを 2 つのセッションが読み込むと連鎖は枝分かれし（A←B と A←C）、
どちらも生きている作業になる。1 件に畳むと、片方が候補一覧から黙って消える。
葉より新しい非葉も、まだ枝が生えていないだけで位相的にはこれと同じ。
§4.4 が session_id 単位でファイルを分けているのは、まさにこの並行セッションのため。

`latest` に記録された session_id を含む行を先頭に置き、印を付ける。
**`latest` がその行の代表（畳んだ先）と一致しないときは、印に `latest` の
session_id を併記する。** 該当する行が複数あるときは全部に付ける。
印だけを貼ると、`latest` が指すものとは中身の違う行を「これが latest」と
表示することになる。

下は枝分かれの例。`9f1c2ab4`（`latest`）を 2 つのセッションが読み込み、
それぞれ `c7a0d3f1` と `2f5b8e13` を作った状態。

```text
このプロジェクトの引き継ぎ:

  1) 2時間0分前  CSV ダウンローダの再試行処理を実装中。テストは赤のまま
     c7a0d3f1-6b28-4e90-a5c4-11d8e2f7b309   （2 件を集約 / latest 9f1c2ab4… を含む）
  2) 5時間12分前 CSV ダウンローダの再試行処理を実装中。仕様は決まったが実装は未着手
     2f5b8e13-40c7-4a19-9e62-8d0fa61b3c25   （2 件を集約 / latest 9f1c2ab4… を含む）
  3) 3日前       型注釈の整備。mypy strict の通過を確認済み
     4b8e1c72-9a04-4f36-8d13-2e5a7c9b0f88   （1 件）

どれを読み込みますか。
```

`9f1c2ab4` 自身は行として出ていない。他から参照されている（葉でない）うえに、
子孫より `updated` が古いため。件数はどちらの行も 2 で、共有している `9f1c2ab4` を
両方で数えている。要約列は `## いま何をしているか` の先頭 1 行をそのまま出す。
状況を説明する文を自分で書かない。

**`updated_by` が `pre-compact-hook` の候補には、その旨を併記する。**
それは `/handoff` を実行しないまま compact が走ったときのスタブで、
git のログしか入っていない。`latest` は「最後に書き込まれた引き継ぎ」であって
「最後に意味情報を書いたもの」ではないので（§4.4）、中身の無いスタブが
`latest` の印を付けて先頭に並ぶことがある。印だけを見て選ばせない。

session_id を併記するのは、要約 1 行が酷似する候補が並んだときに人間が区別できなくなる
のを避けるため。経過時間の表記はフックの `elapsed_ja`（`lib.sh`）に合わせる:
`%d秒前` / `%d分前` / `%d時間%d分前` / `%d日前`。
同じ引き継ぎの鮮度が、フックの注入とこの一覧とで違う書き方になると読み手が混乱する。

**候補が 1 件だけでも人間に確認する。** 並行して別のセッションが動いていると、
`latest` が意図と食い違いうる。確認を省くと、違うものを黙って読み込むことになる。

経過時間は `updated` から計算する。鮮度が見えないと、古い引き継ぎを最新と誤認する。

### 5. 選ばれたファイルを全文読む

`Read` で全文を読む。セクションの取捨選択はしない。

新規セッションはコンテキストが空なので削る動機が無い。ここで削ると、
`handoff` が全セクションを書いた意味が消える（記録は常に全セクション、
量を絞るのは compact 直後の注入だけ、というのが設計）。

### 6. 要約して報告する

人間には「背景・目的」「いま何をしているか」「未完了・次の一手」と、
`updated` からの経過時間を要約して伝える。

```text
引き継ぎを読み込みました（最終更新: 2時間0分前）

背景・目的: 定時バッチが対象 API の 429 で落ちる事象への対処
いま: CSV ダウンローダの再試行処理を実装中。仕様は決まったが実装は未着手
次の一手:
  - test_download_csv.py に 429 応答のテストを追加（テストファースト）
  - 実装は上記テストが赤になってから
```

これは表示の都合であって、コンテキストには全セクションが載っている。
「試して駄目だったこと」や「注意」も読んだうえで作業すること。

### 7. 読み込んだ session_id を覚えておく

このセッションで最初に `handoff` を呼ぶとき、frontmatter の `continues_from` へ
この session_id を書く。手順 4 の集約はこの値だけを頼りにしているので、
書かないと次の仕切り直しで連鎖が切れ、候補一覧に同じ作業が二重に並ぶ。

**読み込んだだけでは compact をまたげない。** `handoff-load` はファイルを書かないので、
このあと `handoff` を呼ばずに compact が走ると、フックは新しい session_id の
スタブを作り、compact 直後に注入されるのは「意味情報は記録されていない」だけになる。
いま読み込んだ引き継ぎはディスクに残っているが、誰も指さない。
読み込んで作業を再開したら、節目で `handoff` を呼ぶこと。
